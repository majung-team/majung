# 픽업 시작 방식과 대기 요청

2026-10-24 기획 결정. 관련 이슈: [#25](https://github.com/majung-team/majung/issues/25). 서비스 시작 방법을 확장하는 계획이며 구현 완료 기록이 아니다.

기준: [팀 노션](https://app.notion.com/p/4026da9ae26a805abd45c0ee5885ef2f). 화면 초안과 분리 시점 문서에 충돌하는 설명이 있으면 이번 결정의 적용 범위는 이 문서를 우선한다. 실제 구현·시험 상태는 각 개발 저장소의 PR과 실행 근거로 확인한다.

## 바꾸려는 이유

운전자가 매번 픽업을 만들고 QR을 찍어 링크를 보내는 일은 번거롭다. 기존 초대 방식은 유지하되, 가족·지인이 필요할 때 먼저 마중을 요청할 수 있도록 한다. 여러 사람을 차례로 태우는 상황도 대기 목록으로 다룬다.

요청을 보내거나 링크를 열었다고 픽업이 시작되는 것은 아니다. 운전자 수락, 경로 반영, 위치 공유 시작은 각각 확인해야 한다.

## 확정한 내용

| 항목 | 결정 |
| --- | --- |
| 시작 방법 | 운전자 초대와 탑승자 요청 모두 지원 |
| 탑승자 요청 진입 | 운전자가 처음 한 번 요청 링크를 전달하고 탑승자가 저장해서 사용 |
| 미응답 요청 | 생성 후 30분에 만료. 수락 전 탑승자가 직접 취소 가능 |
| 픽업 중 새 요청 | 거절하지 않고 대기 목록에 보관 |
| 대기 요청 수락 | 운전자가 미리 수락 가능. 지금 태우러 가는 것과 구분 |
| 주행 중 처리 | 요청 도착만 짧게 안내하고 시스템이 조작을 허용할 때 내용 확인·수락 |
| 수락된 대기 탑승자 | 본인 순서와 본인 장소까지 ETA를 제공하는 방향 |
| ETA 표시 | 누구의 어느 장소까지 계산한 값인지 명시. 계산 근거가 없으면 확인 중 |
| 타인 정보 | 다른 탑승자의 이름·장소·정확한 위치·참여 링크 비공개 |
| 공통 처리 | 픽업 진행 이후 준비 상태·도착·탑승 확인·공유 종료는 같은 처리 사용 |

‘주행 중 알림에서 즉시 수락’은 기본 범위로 확정하지 않았다. 플랫폼 검증 후 검토한다. 화면 밖 수신은 제품 목표지만, 현재 구현됐거나 항상 수신된다고 안내하지 않는다.

## 링크와 연결을 구분한다

| 구분 | 쓰는 때 | 부여하는 권한 |
| --- | --- | --- |
| 이번 픽업 초대 링크 | 운전자가 만든 특정 픽업에 참여 | 해당 픽업 참여 요청. 승인 전 차량 위치 비공개 |
| 마중 요청 링크 | 탑승자가 운전자에게 먼저 요청 | 장소·표시 이름을 제출하는 요청 권한. 차량 위치 조회·픽업 승인 권한 없음 |
| 운전자 휴대전화 연결 | 운전자가 QR 재스캔 없이 초대 공유 | 별도 개선안. 탑승자 요청 링크를 받은 것과 다름 |

요청 링크를 한 번 전달한다는 것은 영구 유효 또는 본인 인증을 뜻하지 않는다. 운전자 철회·재발급, 공유 범위, 유효 기간과 남용 제한은 구현 전에 정해야 한다. 이름만으로 같은 사람이라고 확정하지 않는다.

## 운전자가 먼저 초대하는 흐름

1. 차량에서 내비게이션의 픽업 장소를 확인하고 픽업을 만든다.
2. 차량의 QR을 운전자 휴대전화로 스캔해 이번 픽업 초대를 전달한다. QR은 운전자 공유 화면으로 연결하며, 스캔만으로 탑승자가 되지 않는다.
3. 탑승자가 참여를 요청한다.
4. 운전자가 시스템의 조작 허용 상태에서 참여자를 확인한다.
5. 승인 후 해당 픽업의 위치·ETA와 준비 상태를 공유한다.
6. 도착 뒤 실제 탑승을 확인해 완료한다.

운전자 휴대전화 최초 연결은 반복 QR 스캔을 줄이는 별도 개선안이다. 기존 초대 방식의 필수 전제나 구현 완료 기능으로 적지 않는다.

## 탑승자가 먼저 요청하는 흐름

1. 저장해둔 운전자의 마중 요청 링크를 연다.
2. 장소 검색 또는 지도 선택으로 만날 장소를 정하고 요청한다. 위도·경도 직접 입력을 기본 사용자 흐름으로 쓰지 않는다. 지도 공급자·검색 구현은 별도 작업이다.
3. 서버가 요청을 저장하고 탑승자에게 ‘수락 대기’로 표시한다. 차량에 전달됐다는 근거가 없으면 ‘운전자에게 전달 완료’라고 표시하지 않는다.
4. 운전자는 조작 가능한 상태에서 요청자·장소를 확인해 수락 또는 거절한다.
5. 지금 픽업할 수 있으면 경로 반영 결과를 확인하고 픽업을 시작한다. 기존 픽업이 있으면 ‘수락됨·순서 대기’에 둔다.
6. 앞선 픽업을 완료한 뒤 다음 요청을 확인해 진행한다. 자동 수락이나 임의 경로 변경을 하지 않는다.

요청이 만료·취소됐으면 늦게 도착한 알림을 눌러도 수락하지 못하게 한다. 중복 수락이나 차량·웹 재접속으로 같은 픽업이 두 번 만들어지지 않아야 한다.

## 차량 화면

| 상황 | 표시 | 조작 |
| --- | --- | --- |
| 다른 앱 사용 중 요청 도착 | ‘마중 요청이 도착했어요’ 시스템 알림을 목표로 함 | 강제 화면 전환 없음. 실제 노출은 검증 전 |
| 마중 화면의 주행 제한 상태 | ‘새 마중 요청 1건 · 확인 대기’처럼 짧게 표시하는 기본안 | 상세·수락·장소 변경 제한 |
| 시스템이 조작 허용 | 요청자·장소·요청 시각, 현재 픽업과 대기 목록 | 내용 확인, 수락, 거절 |
| 이미 픽업 중인 요청을 수락 | ‘대기 목록에 추가했어요’ | 현재 픽업을 중단하거나 새 사람 ETA로 덮어쓰지 않음 |
| 다음 픽업으로 전환 | 다음 요청자와 본인 픽업 장소 확인 | 경로 반영 성공 확인 후 전환 |

정차 여부를 임의 속도 기준으로 판단하지 않는다. 실제 CarUxRestrictions에 따른 조작 허용을 사용한다. 신호 대기를 곧바로 조작 가능으로 해석하지 않는다.

## 탑승자 화면과 ETA

### 1. 수락 전

> 수락 대기
> 운전자 확인을 기다리고 있어요.
> 요청 만료까지 24분 · 요청 취소

자신의 요청 장소와 서버 접수 상태만 보여준다. 수락 전 차량 위치와 다른 탑승자의 ETA를 공개하지 않는다.

### 2. 수락 후 순서 대기

> 요청이 수락됐어요
> 앞선 픽업 1건 진행 중 · 내 픽업은 다음 차례
> **내 픽업 장소까지 예상 시간: 확인 중**
> 앞선 픽업 상황에 따라 시간이 달라질 수 있어요.

자기 장소까지 이어지는 경로와 ETA를 검증할 수 있을 때만 숫자를 표시한다. 앞사람까지 5분 남았다고 자기 장소까지 5분이라고 표시하지 않는다. 차량이 앞사람을 태우려고 멈추는 시간은 경로 ETA와 다를 수 있으므로 이를 포함한 보장 시간으로 표현하지 않는다. 임의의 탑승 대기시간을 더해 정확한 수치처럼 만들지 않는다.

‘대기 중’ 한 단어로 수락 전후를 합치지 않는다. 순서는 ‘앞선 픽업 N건’처럼 표시하고 다른 사람의 이름·장소를 노출하지 않는다. 수락된 대기자에게 차량의 실시간 좌표까지 보여줄지는 이번 결정에 포함하지 않는다. 다른 사람의 픽업 위치가 추정될 수 있으므로 기본안은 본인 순서·본인 ETA만 제공한다.

### 3. 본인 픽업 진행

> 내 픽업 진행 중
> **내 픽업 장소까지 약 7분**
> 장소: 내가 선택한 역 입구
> 준비 중 / 준비 완료

화면 예시 숫자는 설명용이다. 실제 SDK·서버 데이터가 아니다. 최신성을 잃으면 기존 끊김 정책과 출처·시각을 함께 처리하며, 알 수 없는 시간을 실시간처럼 카운트다운하지 않는다.

## 요청과 픽업 상태를 나눈다

구현용 이름은 API 명세에서 확정한다. 아래는 화면에 필요한 상태와 전이 기준이다.

| 상태 | 의미 | 다음 처리 |
| --- | --- | --- |
| 수락 대기 | 운전자가 아직 응답하지 않음 | 수락·거절·취소·생성 30분 후 만료 |
| 수락됨·순서 대기 | 운전자가 요청을 받아 대기 목록에 둠 | 본인 순서·검증 가능한 본인 ETA, 다음 픽업 전환 |
| 경로 반영 중 | 해당 장소를 SDK 경로에 반영·확인하는 중 | 성공 시 픽업 시작, 실패 시 대기 유지와 안내 |
| 본인 픽업 진행 | 현재 차량이 처리 중인 픽업 | 도착·탑승 완료·취소·기존 만료 정책 |
| 거절·취소·만료 | 종료된 요청 | 늦은 수락·재전송으로 되살리지 않음 |

30분은 미응답 요청의 수명이다. 수락한 대기 요청을 같은 타이머로 지우지 않는다. 수락된 대기의 최대 유지 시간, 취소·변경 시 알림은 후속 세부 정책으로 남긴다.

기본안: 요청은 접수 순서로 보여주고 운전자가 다음 사람을 선택한다. 자동 최적화, 승차 정원 계산, 하차 구간 관리·탑승 자동 감지는 이번 추가 범위에 포함하지 않는다. 여러 요청이 있다고 여러 픽업을 동시에 ACTIVE로 만들지 않는다. 앞사람 완료로 다음 사람 위치 공유가 자동 시작되지 않아야 한다.

## 구현 순서와 확인 기준

1. 서버 요청 저장·권한·30분 미응답 만료·취소·중복 수락 차단. 요청 링크만으로 위치 조회 불가를 시험한다.
2. 탑승자 장소 선택과 수락 대기 화면, 차량 요청 목록·수락·거절. 이름은 인증이 아님을 유지한다.
3. 수락된 대기 목록과 한 번에 한 픽업 전환. 서로 다른 탑승자 정보 조회 차단을 시험한다.
4. SDK 경로별 자기 장소 ETA 연결. 동일 이름·누락 좌표·순서 변경·재탐색·앞선 픽업 취소 때 다른 사람 ETA가 섞이지 않아야 한다. 숫자를 제공할 수 없는 경우도 정상 화면으로 다룬다.
5. 화면 밖 요청 수신과 실제 시스템 알림. P → D → P, 권한 거절, 다른 앱 사용, 화면 복귀, 프로세스 종료·시동 재시작을 구분해 확인한다.
6. 노션·API 명세·화면 문구와 시연 자료 갱신. 에뮬레이터 통과와 플랫폼 배포 허용·실차 검증은 구분한다.

알림이 불가능해도 서버에 저장된 유효 요청은 차량 앱 복귀 시 조회한다. 탑승자에게 즉시 전달·즉시 응답을 보장하지 않는다. 화면을 강제로 열거나 허용되지 않은 알림 분류를 사용하는 방법으로 우회하지 않는다.

## 남은 세부 설계와 플랫폼 검증

제품의 두 시작 방식은 결정했다. 아래 항목은 확정된 값이 아니므로 구현 명세·시험에서 해소해야 한다.

- 요청 링크의 수명·철회·재발급과 악용 제한, 요청자별 취소 권한과 브라우저 저장 정책
- 수락된 대기 요청의 최대 유지 시간·최대 개수·순서 변경 안내, 운전자 부재·시동 종료 시 표시
- 대기 요청의 장소를 기존 최종 목적지를 유지하며 경로에 넣는 방식과 지점별 ETA 제공 범위
- 일반 알림·헤드업 알림 노출, 알림 권한 거절, 앱 프로세스 종료 뒤 수신·복구
- 주행 중 직접 수락은 기본안 밖이며 검증 후 검토. 문서에 허용된 기능으로 표기하지 않음
- 여행에서 앞사람을 태운 뒤에도 남은 요청을 유지하는 수명. 한 픽업 완료와 전체 요청 대기 목록 종료를 구분

공식 문서와 현재 코드 대조는 [주행 중 요청 알림과 화면 밖 수신 검토](pickup-request-review.md)에 있다.
