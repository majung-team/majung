# 개정 기획과 코드 반영 계획

기준일: 2026-10-23. [팀 노션](https://app.notion.com/p/4026da9ae26a805abd45c0ee5885ef2f)의 07 기능명세서·08 진행 현황·09 MVP·10 역할 분담과 이후 채팅 확정 사항을 대조했다.
기존 01~05의 최초 기획·실험 기록과 현재 기능 요구사항을 구분한다. 같은 항목이 충돌하면 후속 채팅 확정 → 07 상세 명세 → 09 마일스톤 순서로 판단하고, 미확인 기술 조건을 완료로 표시하지 않는다.

## 실행하는 제품과 저장소

| 제품 | 실행 환경·사용자 | 저장소 |
| --- | --- | --- |
| 차량 앱 | Pleos Android Automotive. 운전자 픽업 생성·QR·SDK·주행 표시·음성 안내 | [majung-vehicle-app](https://github.com/majung-team/majung-vehicle-app) |
| 휴대전화 웹 | 브라우저. 운전자 초대 공유 화면과 탑승자 지도·ETA·준비 상태 화면 | [majung-web](https://github.com/majung-team/majung-web) |
| 백엔드 | Spring Boot HTTP API·PostgreSQL·권한·픽업 상태·보관 | [majung-backend](https://github.com/majung-team/majung-backend) |
| 기획·통합 안내 | 저장소 연결·기능별 의존·시연 자료·이전 이력 | [majung](https://github.com/majung-team/majung) |

탑승자 전용 앱은 후속 개발이다. 운전자 휴대전화의 QR 공유 화면도 웹이며 별도 네이티브 앱을 만드는 것이 아니다.
vehicle-app 안의 probe는 SDK 진단 모듈로 유지한다. 별도 출시 앱으로 소개하지 않는다.
두 명 모두 기능별로 서버·웹·차량 코드를 함께 다룬다. 저장소 분리는 담당을 프론트/백엔드로 고정하는 뜻이 아니다.

## 오늘 확정한 사항

- 초대 전달: 차량 QR → 운전자 휴대전화의 공유 화면 → 카카오톡 등으로 탑승자에게 전달.
- 운전자가 먼저 QR을 열어도 탑승자로 소비되지 않도록 공유 화면과 실제 참여 화면을 구분해야 한다.
- 양쪽 모두 장소를 제안할 수 있고 운전자가 최종 확인한다. 초기 픽업 생성과 진행 중 장소 변경을 구분한다. 장소 변경은 2차 범위다.
- 9.1: 관리자가 발급한 일회용 **등록** 코드를 차량에서 최초 한 번 입력한다. 등록 성공 후 차량별 권한을 안전하게 저장하고 픽업마다 코드를 요구하지 않는다. 관리자는 차량별 권한을 철회할 수 있어야 한다.
- 고정 공통 생성 키를 APK에 넣는 안은 채택하지 않는다. 기존 픽업마다 일회용 코드를 소비하는 미커밋 코드는 등록 흐름을 위한 실험 근거로 보존하며 최종 기능 완료로 보지 않는다.

## 작업 순서

1. 저장소별 독립 빌드와 공통 기여 규칙 정리. API 변경은 backend 명세와 각 클라이언트 PR을 서로 연결한다.
2. 승준: MainActivity 영역 분리. 성모: 2.1 자동 연결·2.2 끊기. 두 작업을 먼저 맞춘 뒤 차량 화면 후속 변경을 시작한다.
3. 승준: 9.2 토큰 복구 → 3.2 백그라운드 → 10분 SDK 콜백 간격 측정 → 1.2 경유지 → 5.1 도착.
4. 성모: 1.3 QR → 3.4 끊김 표시 → 3.5 지도. 3.4는 측정 결과를 받아 초기 30초·2분 값을 검토한다.
5. 승준: 8.1 주행 제한·8.2 TTS. 통합 후 1차 시연·release APK·실행 안내 검증.
6. 2차: HTTPS·차량 최초 등록·실제 폰, 자동 종료·7일 보관·집계·동의, 장소 변경·푸시·ack.

노션의 1차는 11/15, 2차 PT는 12/3으로 기획돼 있다. 이는 팀 문서의 일정이며 주최 측 공고를 이 분석에서 다시 검증한 결과는 아니다. 제출·계정 초대·동의서 서명은 별도 실제 확인이 필요하다.

## 문서에서 보완해야 할 지점

- 07·08의 고정 키/일회용 코드 충돌은 위 최초 등록 방식으로 해소됐다. 본문 표와 역할 분담의 9.1 설명도 수정해야 한다.
- 09 핵심 시나리오는 QR을 운전자가 스캔해 탑승자에게 전달하지만 1.4 공유를 2차로 배치한다. 1차 시연에서 최소한 링크 복사/OS 공유 흐름은 필요하다. 카카오 SDK 전용 공유 고도화와 구분한다.
- 07의 원본 7일 보관과 차량 좌표·ETA 종료 즉시 삭제가 같은 데이터에 겹치지 않게 컬럼별 파기 기준을 정한다. 종료 후 조회 차단만으로 실제 삭제를 완료했다고 보지 않는다.
- 위치 STALE 보존은 명시적 SDK 해제·경로 변경 무효화·종료 후 차단을 되돌리면 안 된다. 각 원인의 상태·응답·웹 표시를 따로 검증한다.
- QR의 운전자 공유 페이지를 탑승자 자동 참여로 처리하면 운전자가 초대를 먼저 소비한다. URL/토큰 용도와 실제 참여 시점을 분리한다. 링크 미리보기 GET 요청도 초대를 소비하지 않도록 한다.
- EXPIRED는 실제 상태 변경·토큰 복구·백그라운드 중지까지 연결한다. 최대 시간 설정만 12시간으로 바꾸면 무활동·도착 후 종료를 구현한 것이 아니다.
- 앱 재시작 복구, OS 프로세스 재생성, 사용자의 강제 중지는 같은 조건이 아니다. 검증과 보장 범위를 나누어 기록한다.
- 좌표만으로 경유지를 식별할 때 동일 좌표 중복·근접 오차·순서 변경·재탐색을 다룰 기준이 필요하다. SDK 응답을 보고 판별하며 추측으로 다른 지점 ETA를 공유하지 않는다.
- TTS SDK 이용 조건, Foreground Service 제한, DO·주행 화면 허용은 플랫폼 검증 항목이다. 팀의 채택 결정을 심사 통과로 표현하지 않는다.
- EncryptedSharedPreferences 등 저장 수단은 실제 Android 지원 상태와 키 수명·백업 정책을 확인해 선택한다. 이 문서가 특정 라이브러리의 지원 상태를 보증하지 않는다.
- 08의 GCP 미생성·DB 복구 미검증은 새 비공개 VM 시험 결과보다 이전 기록이다. 코드 main 반영, 서버에 적용한 시험, 공개 HTTPS 완료를 따로 표시한다.
- 일부 이전 계정 링크가 '사용 권한 없음'으로 보인다. 현재 페이지 ID로 연결을 바꿔야 한다.

## 검증 기준

분리 검증은 기존 main의 서버 25개·차량 단위 8개·웹 모델 5개와 독립 빌드·HTTP 연결로 확인한다.
기존 원본 저장소의 초안 모델 8개는 실제 웹 테스트와 합산해 기능 완료로 주장하지 않는다.
새 계획의 자동 연결·백그라운드·경유지·지도·주행 제한·등록 권한 등은 각각 구현 PR과 검증 근거가 있어야 완료다.
