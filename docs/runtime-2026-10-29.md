## 2. Blue-Green 배포 구조

마중 백엔드는 하나의 VM에서 Blue와 Green 애플리케이션을 번갈아 실행하는 방식으로 배포한다.

새 버전을 기존 서버와 별도로 실행하고 정상 동작을 확인한 뒤 Caddy의 연결 대상을 전환한다.

### 구성

| 구성 요소 | 역할 |
| --- | --- |
| Blue | 애플리케이션 실행 슬롯 · 포트 `8081` |
| Green | 애플리케이션 실행 슬롯 · 포트 `8082` |
| Caddy | 공개 HTTPS 요청을 활성 슬롯으로 전달 |
| PostgreSQL | 애플리케이션 데이터 및 공유 로그인 세션 관리 |
| GitHub Actions | 새 버전 배포, 상태 확인 및 전환 자동화 |

로그인 세션은 PostgreSQL에 저장하여 두 애플리케이션 슬롯에서 공유한다.

이를 통해 배포 전환 시 새로운 서버에서도 기존 세션을 조회할 수 있도록 구성했다.

> Blue-Green은 애플리케이션 배포 전환을 위한 구조다. VM과 PostgreSQL 자체를 이중화한 고가용성 구성은 아니다.

## 3. 실제 배포 전환 과정

### 3.1 초기 전환 준비

1. 마중 PostgreSQL 데이터베이스 백업
2. 공유 세션 테이블 2개 및 애플리케이션 계정 권한 추가
3. 기존 픽업 테이블 및 데이터 유지
4. JDBC 공유 세션 코드 반영
5. 기존 `8080` 환경에서 Blue `8081` 슬롯으로 이전

데이터베이스 구조 변경 과정에서 기존 픽업 테이블을 삭제하지 않았다.

### 3.2 Blue → Green 전환

1. Blue 슬롯에서 기존 서비스 유지
2. GitHub Actions를 수동 실행하여 Green `8082` 슬롯에 동일 커밋 배포
3. 후보 서버의 DB 연결 및 세션 테이블 확인
4. 배포 커밋과 활성 슬롯 확인
5. 후보 서버 상태 확인
6. Caddy 연결 대상을 Green으로 전환
7. 전환 후 공개 서비스 확인
8. 이전 슬롯 종료

**실행 기록**

[GitHub Actions · Blue → Green](https://github.com/majung-team/majung-backend/actions/runs/40826338867)

### 3.3 Green → Blue 전환

이후 새로운 커밋을 대상으로 자동 배포를 실행했다.

1. Green 슬롯에서 기존 서비스 유지
2. 새로운 커밋을 Blue 슬롯에 배포
3. 후보 서버 상태 및 공유 세션 확인
4. Caddy 연결 대상을 Blue로 전환
5. 공개 서비스 정상 동작 확인
6. 이전 Green 슬롯 정리

**실행 기록**

[GitHub Actions · Green → Blue](https://github.com/majung-team/majung-backend/actions/runs/40827888795)

### 3.4 전환 후 상태 확인

배포 이후 다음 항목을 대조했다.

- 활성 슬롯 기록 파일
- 실제 실행 중인 애플리케이션 서비스
- GitHub Actions 배포 상태
- 공개 요청을 처리하는 서버 슬롯
- 재부팅 시 자동 시작하도록 설정된 서비스

각 정보가 동일한 활성 슬롯을 가리키는지 확인했다.

## 4. 배포 전환 검증 결과

### HTTP 요청 확인

| 테스트 구간 | 요청 횟수 | HTTP 실패 |
| --- | ---: | ---: |
| 최초 전환 공개 health 확인 | 70회 | 0회 |
| GitHub Actions 전환 구간 | 159회 | 0회 |

해당 시험 구간에서는 공개 HTTP health 요청의 실패가 관측되지 않았다.

다만 이 결과가 모든 요청이나 네트워크 조건에서 중단이 전혀 발생하지 않음을 보장하지는 않는다.

### 세션 및 인증 상태

Blue와 Green 슬롯이 동일한 PostgreSQL 기반 세션 저장소를 사용하도록 구성했다.

확인한 항목은 다음과 같다.

- 두 HTTP 서버에서 사용자 세션 공유
- CSRF 상태 공유
- 세션 기반 요청 처리
- 한 슬롯의 로그아웃 결과가 다른 슬롯에 반영되는지 확인
- 배포 전환 전 발급한 익명 세션과 CSRF를 이용한 전환 후 로그아웃 확인

전환 후 로그아웃 요청에서 HTTP `204` 응답을 확인했다.

실제 로그인은 동일 시험 DB를 사용하는 두 HTTP 서버에서 검증했다.

> 운영 카카오 계정으로 배포 전후 반복 로그인한 결과는 아니다. 시험 DB에서 수행한 세션·CSRF 공유 검증과 실제 OAuth 로그인 검증은 구분한다.

## 5. 자동화 테스트 결과

| 테스트 구분 | 결과 |
| --- | --- |
| 서버 테스트 | 총 100건 중 99건 통과 |
| 선택 실행 대상 | 1건 제외 |
| 배포 자동화 테스트 | 13건 통과 |

### 배포 실패 복구 검증

자동화 테스트에서 다음 상황의 복구 동작을 확인했다.

- 후보 서버 실행 또는 확인 실패
- 공개 서비스 확인 실패
- Caddy reload 실패
- 실패 시 기존 활성 슬롯 유지 및 복구 처리

이 결과는 자동화 테스트 환경에서 실패 조건을 재현한 것이다.

실제 운영 서버에 의도적으로 장애를 발생시켜 검증한 결과는 아니다.

### SSE 연결 처리

Blue-Green 전환 과정에서 기존 SSE 연결이 끊길 수 있다.

모바일 웹은 연결을 다시 시도하고, 재연결 후 API를 호출하여 현재 픽업 상태를 다시 조회한다.

SSE 변경 신호만으로 현재 상태를 판단하지 않고 서버의 최신 데이터를 기준으로 화면을 갱신한다.

## 6. 차량 앱 및 모바일 웹 변경 사항

### 차량 앱

**최초 이용 및 위치 공유**

- 첫 실행 시 위치 공유 안내 제공
- 사용자 동의 상태 저장
- 동의 철회 기능
- 동의 전 위치 공유 차단

**장소 제안 및 경로 검증**

- 탑승자가 제안한 장소를 기존 장소와 별도 카드로 표시
- 차량 내비게이션 SDK에서 경로 및 ETA 확인
- 경로 검증 후 제안 장소 확정
- 장소 버전 변경 반영

공식 SDK와 로컬 API 기반 시험에서 다음 내용을 확인했다.

- 기존 최종 목적지 유지
- 다른 경유지 유지
- 제안 장소 경로 검증
- 연결 복구
- 장소 버전 `2` 반영

**차량 화면**

- 내용이 없는 섹션 숨김
- 불필요한 빈 화면 영역 제거
- 상태에 따른 화면 표시 개선

### 모바일 웹

**초대 링크 재접속**

같은 브라우저 탭에서 뒤로 이동한 뒤 초대 링크를 다시 열었을 때 기존 참여 상태를 복구하도록 개선했다.

다음 상황은 복구 대상에서 제외한다.

- 다른 픽업에 대한 참여
- 이미 종료된 픽업
- 참여 권한이 철회된 픽업

브라우저 탭 종료나 다른 브라우저에서의 복구는 별도 검증 범위다.

**개인정보 안내**

[마중 개인정보 안내](https://majung.cloud/privacy)

- 위치 정보 공유 범위 안내
- 데이터 보관 및 정리 정책 안내
- 운영자 문의 정보 제공
- 모바일 크기 화면 표시 확인
