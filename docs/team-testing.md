# 팀 테스트 안내

시험할 때 이 문서를 열어두고 위에서부터 확인하면 된다. 최신 변경은 [10월 29일 운영 확인](runtime-2026-10-29.md)을 함께 본다. 서버·웹 배포 성공과 공개 health·로그인 전 접근 차단을 확인했다. 시험할 때도 실제 배포 커밋을 먼저 확인한다.

## 먼저 열어볼 주소

| 주소 | 확인할 내용 |
| --- | --- |
| https://majung.cloud/ | 픽업 초대·참여 웹. 초대 링크 없이 열면 진행 중인 픽업이 자동으로 보이지는 않는다. |
| https://majung.cloud/account | 카카오 로그인, 닉네임, 사람 검색·연결. 현재 버전에서 마중 요청도 여기서 보낸다. |
| https://majung.cloud/privacy | 위치 공유·보관 기준과 운영자 문의 |
| https://majung.cloud/api/v1/health | 서버 상태. `status`가 `UP`인지 확인한다. `revision`은 배포된 서버 커밋이다. |
| https://majung.cloud/release.json | 배포된 웹 커밋 확인. 서버와 별도 저장소라 커밋 값이 다른 게 정상이다. |

Swagger 화면은 아직 붙이지 않았다. 요청 주소와 입력값은 맨 아래 서버 API 문서를 참고한다.

서버에 SSH로 접속하지 않아도 기능을 시험할 수 있다. GCP 권한이나 관리자 키는 탑승자·운전자 테스트에 필요 없다. 관리자 키는 서버에만 둔다. 위 주소는 마중 전용이며 플리플리 주소와 다르다.

## 지금 되는 것과 새 버전에서 확인할 것

카카오 로그인·닉네임·사람 검색과 기존 초대 픽업, 새 탑승자의 장소 포함 요청·여러 요청 대기·운전자 계정과 차량 연결은 main에 반영됐다. 아래 PR은 해당 기능의 반영 기록이다.

| 순서 | 반영할 내용 | 링크 |
| --- | --- | --- |
| 1 | 서버의 운전자 계정 연결·마중 요청·대기열 | [백엔드 PR #16](https://github.com/majung-team/majung-backend/pull/16) |
| 2 | 휴대전화의 차량 연결·요청·대기 화면 | [웹 PR #15](https://github.com/majung-team/majung-web/pull/15) |
| 3 | 차량의 계정 연결·받은 요청·다음 픽업 | [차량 PR #24](https://github.com/majung-team/majung-vehicle-app/pull/24) |

세 PR은 main에 반영됐다. Actions에서 서버·웹의 배포 성공을 확인한다. 다음에 API 변경이 생겨도 서버를 먼저 배포하고 웹을 반영한다. 차량은 머지만으로 바뀌지 않으므로 새 APK를 설치한다. CI가 실패하면 먼저 원인을 고치고 통과한 커밋으로 진행한다.

최신 배포 커밋은 [10월 29일 기록](runtime-2026-10-29.md)과 health·release.json을 대조한다. 이전 PR 번호만 보고 실제 배포 완료로 판단하지 않는다.

서버·웹은 각 저장소의 main에서 GitHub Actions로 배포된다. 한 저장소의 코드를 다른 저장소에 복사해 합치는 방식이 아니다. 같은 서버에서 Caddy가 웹을 제공하고 `/api/` 요청을 백엔드로 전달한다. 차량 APK도 같은 HTTPS API를 호출한다.

DB는 마중 전용 서버에서 백업 후 새 테이블 3개와 실행 권한을 준비했다. 이 준비로 앱 서버를 재시작하지는 않았다. 회의 중 SQL을 다시 실행할 필요는 없다.

## 회의 전에 준비할 것

- 두 사람 모두 조직의 비공개 저장소를 열 수 있는지 확인한다.
- 운전자 역할은 Pleos 에뮬레이터와 차량 APK를 준비한다. QR을 읽을 휴대전화도 필요하다.
- 탑승자 역할은 휴대전화 브라우저와 본인 카카오 계정을 준비한다.
- 두 사람의 닉네임은 알아보기 쉽게 다르게 정한다. 동명이인은 마중 ID로 구분한다.
- 처음 쓰는 차량은 ‘휴대전화로 시작하기’ QR로 운전자 계정을 연결한다. 관리자 등록 코드는 필요 없다.
- 운전자와 탑승자는 서로 다른 카카오 계정으로 로그인한다. 브라우저 창만 두 개 여는 것으로 서로 다른 사람이 되지는 않는다.

## 차량 앱 설치

바로 시험하려면 [0.2.14-preview 서명 APK](https://github.com/majung-team/majung-vehicle-app/releases/tag/v0.2.14-preview.20261029)를 받는다. [설치와 최초 설정](wiki/차량-앱-설치.md)에 따라 설치한다. 직접 빌드하려는 경우 아래 방법을 사용한다.

Android Studio가 필요한 건 빌드·에뮬레이터 준비 단계다. 설치한 앱은 에뮬레이터의 앱 목록에서 직접 실행할 수 있다.

```sh
git clone https://github.com/majung-team/majung-vehicle-app.git
cd majung-vehicle-app
npm ci
```

JDK 25, Android SDK API 34, 공식 Pleos 에뮬레이터를 준비한다. `local.properties`에는 각자 설치한 SDK 경로를 넣는다.

```properties
sdk.dir=/각자/설치한/Android/sdk
```

```sh
./gradlew :vehicle:assembleDebug -PpickupApi=https://majung.cloud
adb devices
adb install -r vehicle/build/outputs/apk/debug/vehicle-debug.apk
adb shell am start --user current -n app.majung.vehicle/.MainActivity
```

`adb`를 찾지 못하면 Android SDK의 `platform-tools` 경로를 PATH에 추가한다. 장치가 둘 이상이면 `adb -s 장치이름 install -r ...`처럼 시험할 장치를 지정한다. 처음부터 앱 데이터 삭제나 에뮬레이터 초기화를 하지 않는다.

Android Studio 밖에서 에뮬레이터를 띄우려면 SDK의 `emulator` 명령으로 설치된 AVD를 확인한 뒤 해당 이름으로 실행한다. Android Studio의 Device Manager에서 실행해도 같은 장치다.

```sh
emulator -list-avds
emulator -avd "확인한 Pleos AVD 이름" -no-snapshot-save
```

공개 서버 시험에서는 `-PpickupApi=https://majung.cloud`를 빼지 않는다. 기본 debug 빌드는 개발 PC의 로컬 서버를 가리킨다. 휴대전화의 `localhost`는 개발 PC나 GCP 서버가 아니다.

첫 실행에서는 위치 공유 안내를 읽고 동의한 뒤 시작한다. 앱에서 **휴대전화로 시작하기 · QR 만들기**를 누른다. 운전자 휴대전화에서 카카오 로그인 후 연결을 요청하고 차량에서 닉네임·마중 ID를 확인한다. 등록과 계정 연결이 한 번에 끝난다. 이전에 등록된 차량은 다시 등록하지 않는다.

## 두 사람이 먼저 확인할 순서

### 1. 로그인과 운전자 찾기

각자 휴대전화에서 `/account`를 열어 로그인하고 닉네임을 정한다. 탑승자는 운전자의 닉네임을 검색하고 마중 ID까지 확인한다. 실제 카카오 비밀번호나 인증 코드를 서로 전달하지 않는다.

### 2. 운전자와 차량 연결 — 새 버전에서

새 차량은 앞 단계에서 운전자 연결도 끝났으므로 바로 다음 단계로 간다. 기존 관리자 코드로 등록했지만 계정은 연결하지 않은 차량만 **운전자 계정 연결 QR 만들기**를 누른다. 본인 휴대전화로 QR을 열고 **이 계정으로 차량 연결 요청**을 누른다. 차량에 표시된 닉네임·마중 ID가 본인인지 확인하고 승인한다.

휴대전화에서 요청만 했을 때는 아직 연결되지 않아야 한다. 차량에서 승인한 뒤 휴대전화의 내 차량에 표시되는지 확인한다. QR은 5분 뒤 만료된다. 탑승자는 이 QR을 스캔하지 않아도 된다.

### 3. 처음 보는 탑승자가 요청하기 — 새 버전에서

탑승자는 검색 결과의 **마중 요청**을 누른다. **현재 위치 선택**에서 위치 권한을 허용하고, ‘정문 앞 주차장 입구’처럼 만날 장소를 적는다. 요청을 보내면 **운전자 응답 대기**가 표시돼야 한다.

기존에 사람 연결을 해둔 적이 없어도 요청할 수 있다. **연결만 요청**은 별도 기능이라 먼저 누를 필요가 없다. 현재 위치 또는 지도 검색으로 장소를 고를 수 있다. 검색 결과나 지도 지점을 직접 선택한 뒤 장소 이름을 확인하고 전송한다. 지도만 열었다고 기본 중심점이 선택되지는 않는다.

위치가 선택되지 않으면 요청을 보낼 수 없다. 브라우저 위치 권한과 휴대전화 GPS를 확인한다. 오차가 300m보다 크면 다시 선택하도록 안내한다. 장소를 선택한 뒤 2분이 지나면 위치를 다시 선택한다.

### 4. 차량에서 수락하고 픽업 시작하기

차량의 **받은 마중 요청과 픽업 대기 목록**을 열어 사람과 장소를 확인한다. 수락하면 탑승자 화면이 **수락됨 · 픽업 대기**로 바뀌어야 한다. 아직 위치 공유가 시작된 것은 아니다.

내비게이션에 최종 목적지와 경로를 먼저 설정한다. 마중에서 내비게이션을 연결한 뒤 요청 장소를 경유지에 추가한다. SDK가 같은 장소의 경로를 확인한 뒤 **이 픽업 시작**을 누른다. 계속하기로 공유를 확인한다. 경로 확인이 실패하면 시작을 강행하지 말고 화면에 나온 이유를 기록한다.

탑승자 화면에서 **내 픽업 진행 중**으로 바뀌고, 새 SDK 정보가 들어오면 자기 장소까지 ETA가 표시돼야 한다. SDK 정보가 없으면 시간을 지어내지 않고 기다리는 안내를 보여야 한다.

### 5. 준비 완료·도착·탑승 완료

탑승자가 **준비 완료**를 누른 뒤 차량에 같은 상태가 보이는지 확인한다. 개발 시험에서는 **도착 알리기 · 공유 유지**로 도착 상태를 확인할 수 있다. 이 버튼 시험을 SDK 자동 도착 시험으로 기록하지 않는다.

실제 탑승을 확인하는 흐름에서 **탑승 확인 · 픽업 완료**를 누른다. 종료 후에는 이전 차량 위치와 ETA가 보이지 않아야 한다. 다음 요청은 **새 픽업 준비**를 누른 뒤 진행한다.

## 두 번째·세 번째 요청 확인

운전자가 한 사람을 픽업 중이어도 다른 사람이 새로 요청할 수 있다. 운전자가 수락하면 대기에 들어가고 현재 픽업을 마치기 전에는 다음 요청을 시작할 수 없어야 한다.

대기자 화면에서는 자기 앞의 요청 수만 확인한다. 다른 탑승자의 이름·장소·좌표는 나오면 안 된다. ‘현재 진행 중인 픽업까지 약 N분’은 대기자 자신의 도착 예정 시간이 아니다. 그 차이가 화면에서도 분명해야 한다.

실제 계정으로 운전자 한 명·탑승자 두 명을 동시에 시험하려면 카카오 계정이 세 개 필요하다. 개발자가 두 명인 회의에서는 우선 운전자·탑승자 한 명의 흐름을 직접 확인하고, 여러 요청은 아래 가상 계정 자동 시험 결과를 함께 본다. 같은 탑승자가 같은 운전자에게 열린 요청을 여러 번 보내는 것은 중복 요청으로 막는다.

```sh
# majung-backend 저장소에서 실행
./gradlew test --tests '*RideRequestTest'
```

이 시험에는 신규 탑승자 세 명의 요청·대기·차례 전환, 동시 수락의 순서 분리, 기존 초대 픽업 중 새 요청 수락, 중복·취소·만료·타인 접근·계정 해제가 포함돼 있다. 가상 계정 시험과 실제 휴대전화 시험은 따로 기록한다.

## 이상하면 여기부터 확인

| 증상 | 먼저 확인할 것 |
| --- | --- |
| 사이트가 열리지 않음 | 휴대전화 데이터 연결, 정확한 HTTPS 주소, health 응답 |
| health는 UP인데 새 버튼이 없음 | 웹 PR의 배포 성공과 release.json 확인, 새로고침 |
| 웹은 바뀌었는데 요청이 404·준비 중으로 나옴 | 서버 PR이 먼저 배포됐는지 확인 |
| 서버 배포 뒤 로그인이 풀림 | 다시 로그인. 저장된 차량 등록을 지우거나 새 코드를 입력할 필요는 없음 |
| 차량 앱만 연결 안 됨 | 공개 서버 주소로 빌드했는지, 차량 등록 상태, 인터넷 연결 |
| 차량 미연결이라 요청 불가 | 운전자가 카카오 계정 연결을 차량에서 승인했는지 확인 |
| 같은 이름이 여러 명 | 닉네임만 보고 누르지 말고 마중 ID 확인 |
| 위치 선택 안 됨 | HTTPS, 브라우저 위치 권한, 휴대전화 GPS와 정확도 확인 |
| 버튼이 잠김 | 주행 제한 상태인지 확인. 에뮬레이터를 안전한 P 상태로 전환 |
| ETA가 없거나 사라짐 | SDK 연결·경로·목적지 일치·새 정보 수신 여부 확인. 모르는 시간을 계속 표시하지 않는 게 정상 |
| 요청·수락 결과를 못 받음 | 목록을 새로 확인. 같은 작업을 연속으로 반복하지 않기 |
| 새 요청이 바로 안 보임 | 차량 앱을 열고 새로 확인. 앱 종료 상태의 요청 푸시는 아직 없음 |

다른 서비스가 안 된다고 플리플리 인스턴스를 재시작하거나 설정을 바꾸지 않는다. 마중 서버와 분리돼 있다.

## 회의에서 남길 기록

정상 흐름을 먼저 한 번 끝낸 뒤 예외 상황을 확인한다. 아래 정도만 남겨도 다음 수정 때 도움이 된다.

```text
확인한 날짜:
서버 revision / 웹 revision:
차량 앱 커밋:
시험한 기기·에뮬레이터:
어느 단계에서:
기대한 결과:
실제로 보인 결과:
다시 해도 같은지:
관련 이슈:
```

초대 링크 원문·등록 코드·차량 권한·로그인 쿠키·실제 위치는 이슈나 화면 캡처에 넣지 않는다. 재현에 필요한 단계와 오류 코드만 남긴다.

## 아직 직접 확인할 것

실제 휴대전화의 QR 스캔·GPS·브라우저 권한, 새 요청 장소를 SDK 경로에 반영하는 전체 흐름, 실제 두 카카오 계정의 새 요청 흐름은 회의에서 확인할 항목이다. 로컬·에뮬레이터 결과가 실차 검증을 대신하지는 않는다.

## 연결된 탑승자 직접 초대 시험

서버 PR #18·웹 PR #17·차량 PR #29는 main에 반영됐다. 서버·웹과 마중 DB 추가 컬럼도 배포했다. 차량의 새 APK를 설치한 뒤 확인한다.

1. 두 사람이 `/account`에서 로그인하고 서로 연결 요청·수락을 마친다. 운전자만 차량 계정을 연결한다.
2. 차량에서 내비 장소를 확인하고 ‘연결된 탑승자에게 초대 보내기’로 상대를 선택한다.
3. 탑승자는 같은 `/account`의 받은 초대에서 장소를 확인하고 수락한다. 수락 전 차량 위치가 보이지 않아야 한다.
4. 차량에서 대기 목록을 확인한다. 다른 픽업이 진행 중이면 기존 픽업 뒤에 들어가야 한다.
5. 앞선 픽업을 마친 뒤 초대한 사람의 픽업을 시작하고 공유를 확인한다.

QR을 다시 찍지 않는 흐름이다. 웹을 닫아둔 동안에는 초대 알림이 오지 않는다. 공개 서버의 로그인은 확인했다. 두 계정으로 직접 초대를 주고받는 전체 흐름은 아직 로컬 시험 범위다.

### 10월 26일 배포 기록

서버 PR #18의 첫 배포는 `ride_request.driver_invitation` 컬럼 누락으로 시작에 실패했고 이전 버전으로 복구됐다.
마중 DB에 컬럼을 추가한 뒤 같은 Actions 실행의 실패한 배포 작업을 다시 실행해 성공했다.
기존 요청과 사용자를 지우거나 DB를 새로 만들지 않았다. 휴대전화의 카카오 브라우저 경고와 이 서버 오류가 같은 원인이었다고 단정하지 않는다.

## 준비 상태 전달과 장소 선택 — 10월 26일 추가

새 차량 APK를 설치한 뒤 시험한다. 서버·웹만 최신이어도 이전 차량 APK는 수신 확인을 보내지 않는다.

1. 탑승자 화면에서 준비 완료를 누른다. 먼저 ‘서버에 저장 · 차량 전달 대기’가 표시되는지 확인한다.
2. 차량이 상태를 조회하면 ‘차량 앱에 전달’로 바뀌는지 확인한다. 운전자가 읽었다는 뜻은 아니다.
3. 차량 앱을 닫아 공유 서비스도 멈춘 상태에서 준비 상태를 다시 바꾼다. 이전 상태의 전달 완료가 남아 있지 않아야 한다.
4. 탑승자가 새 마중 요청을 만들 때 장소명·주소를 검색하고 결과의 이름·주소를 확인한다. 선택한 핀과 설명을 확인한다. 직접 지도에서 만날 지점을 골라도 된다. 지도만 열고 선택하지 않으면 보낼 수 없어야 한다. 현재 위치 선택도 계속 사용할 수 있다.
5. 운전자가 받은 장소를 확인하고 수락한다. 이후 기존 순차 픽업 흐름으로 시작한다.

[추가 기능·검증 기록](readiness-place-2026-10-26.md)을 참고한다. 실제 휴대전화 GPS와 실차 경로 시험은 아직 별도다.
