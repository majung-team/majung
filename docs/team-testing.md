
# 팀 테스트 안내

마중 차량 앱과 모바일 웹, 백엔드 서버를 연결해 주요 기능을 확인하는 테스트 가이드다.

운전자와 탑승자가 서로 다른 계정을 사용하여 픽업 요청부터 탑승 완료까지의 흐름을 검증한다.

**기준일: 2026년 10월 30일**

> 이 문서는 테스트 절차를 설명한다. 아래 항목이 모두 실제 휴대전화나 차량에서 검증 완료됐다는 뜻은 아니다.
>
> 현재 운영 버전과 배포 기록은 [운영 버전 및 배포 검증](runtime-2026-10-29.md)을 참고한다.

## 1. 테스트 환경 및 접속 주소

### 주요 주소

| 주소 | 확인 내용 |
| --- | --- |
| [마중 웹](https://majung.cloud/) | 픽업 초대 링크 및 참여 화면 |
| [계정·픽업 관리](https://majung.cloud/account) | 카카오 로그인, 사람 검색·연결, 픽업 요청 |
| [개인정보 안내](https://majung.cloud/privacy) | 위치 정보 공유 및 보관 기준 |
| [서버 health](https://majung.cloud/api/v1/health) | 서버 상태 및 배포 커밋 |
| [웹 release.json](https://majung.cloud/release.json) | 현재 웹 배포 커밋 |

서버 health 응답의 `status`가 `UP`인지 확인한다.

서버의 `revision`과 웹 `release.json`은 각각 별도 저장소의 배포 커밋을 나타내므로 값이 달라도 정상이다.

웹 주소만 열었다고 진행 중인 픽업이나 차량 위치가 자동으로 공개되지는 않는다.

Swagger 화면은 현재 제공하지 않는다. API 요청 형식은 [서버 API 문서](https://github.com/majung-team/majung-backend/blob/main/docs/ride-requests.md)를 참고한다.

일반적인 서비스 테스트에는 서버 SSH 접속, GCP 관리자 권한 또는 관리자 키가 필요하지 않다.

### 테스트 준비물

| 역할 | 준비 사항 |
| --- | --- |
| 운전자 | 카카오 계정, QR을 읽을 휴대전화 |
| 탑승자 | 운전자와 다른 카카오 계정, 모바일 웹브라우저 |
| 차량 | Pleos Connect 공식 에뮬레이터 |
| 차량 앱 | 마중 공개 HTTPS 서버로 연결되는 APK |
| 개발 환경 | Android Studio, JDK, Android SDK, ADB |

운전자와 탑승자는 반드시 서로 다른 계정을 사용한다.

브라우저 창을 두 개 여는 것만으로 서로 다른 사용자가 되는 것은 아니다.

닉네임이 같은 경우에는 마중 ID로 계정을 구분한다.

## 2. 차량 앱 설치

### 서명 APK 설치

별도의 빌드 없이 테스트하려면 GitHub Releases에서 APK를 내려받는다.

[차량 앱 v0.2.16-preview](https://github.com/majung-team/majung-vehicle-app/releases/tag/v0.2.16-preview.20261031)

공식 Pleos 에뮬레이터를 실행한 뒤 설치한다.

```sh
adb devices
adb -s emulator-5554 install -r ~/Downloads/Majung_Majung_release.apk
```

`emulator-5554`는 실제 연결된 에뮬레이터 이름으로 변경한다.

기존 개발용 APK와 서명이 다른 경우에는 덮어쓰기 설치가 실패할 수 있다.

기존 앱을 삭제하면 로컬 차량 연결 정보가 사라질 수 있으므로, 진행 중인 픽업과 재등록 필요 여부를 먼저 확인한다.

### 직접 빌드하기

차량 앱 소스코드를 사용하려면 다음 저장소를 준비한다.

```sh
git clone https://github.com/majung-team/majung-vehicle-app.git
cd majung-vehicle-app
npm ci
```

개발 환경:

- JDK 25
- Android SDK API 34
- 공식 Pleos 에뮬레이터
- Android SDK Platform Tools

각 개발 환경의 SDK 경로를 `local.properties`에 설정한다.

```properties
sdk.dir=/각자/설치한/Android/sdk
```

공개 서버를 대상으로 빌드한다.

```sh
./gradlew :vehicle:assembleDebug -PpickupApi=https://majung.cloud
```

에뮬레이터 연결 상태 확인:

```sh
adb devices
```

APK 설치:

```sh
adb install -r vehicle/build/outputs/apk/debug/vehicle-debug.apk
```

앱 실행:

```sh
adb shell am start --user current -n app.majung.vehicle/.MainActivity
```

공개 서버 시험에서는 `-PpickupApi=https://majung.cloud`를 반드시 지정한다.

기본 Debug 빌드는 개발 PC의 로컬 서버를 가리킬 수 있다.

### 에뮬레이터 직접 실행

설치된 AVD 목록을 확인한다.

```sh
emulator -list-avds
```

사용할 Pleos AVD를 실행한다.

```sh
emulator -avd "확인한 Pleos AVD 이름" -no-snapshot-save
```

Android Studio Device Manager에서 실행해도 된다.

에뮬레이터가 이미 실행 중이라면 중복으로 실행하지 않는다.

## 3. 차량 최초 등록 및 계정 연결

처음 사용하는 차량은 QR코드로 운전자 계정과 연결한다.

### 연결 순서

1. 차량 앱 실행
2. 위치 공유 안내 확인 및 동의
3. **휴대전화로 시작하기 · QR 만들기** 선택
4. 운전자 휴대전화로 QR코드 열기
5. 카카오 로그인 및 닉네임 설정
6. **이 계정으로 차량 연결 요청** 선택
7. 차량에서 요청한 계정의 닉네임·마중 ID 확인
8. **이 계정으로 연결** 선택
9. 휴대전화의 내 차량 목록에서 연결 상태 확인

QR코드는 생성 후 5분간 유효하다.

휴대전화에서 연결을 요청한 것만으로 등록이 완료되지는 않는다. 차량에서 최종 승인해야 한다.

이미 등록된 차량은 기존 연결 상태를 확인하고 필요한 경우에만 다시 연결한다.

탑승자는 차량 등록이나 운전자 연결 QR을 사용할 필요가 없다.

## 4. 기본 픽업 테스트

운전자 1명과 탑승자 1명이 서로 다른 계정으로 진행한다.

### 4.1 로그인 및 운전자 검색

**운전자**

1. `/account` 접속 및 카카오 로그인
2. 닉네임과 마중 ID 확인
3. 차량 계정 연결 상태 확인

**탑승자**

1. `/account` 접속 및 카카오 로그인
2. **사람 찾기**에서 운전자 검색
3. 닉네임과 마중 ID 확인

실제 카카오 비밀번호나 인증 코드를 서로 전달하지 않는다.

### 4.2 탑승자가 먼저 요청하기

1. 검색한 운전자의 **마중 요청** 선택
2. 장소명·주소 검색 또는 지도에서 위치 선택
3. 장소 이름, 주소 및 지도 핀 확인
4. 요청 전송
5. **운전자 응답 대기** 표시 확인

기존에 운전자와 연결된 관계가 없어도 요청할 수 있다.

**연결만 요청**은 별도 기능이며, 픽업 요청 전에 반드시 진행해야 하는 과정은 아니다.

장소를 검색하거나 지도만 열어둔 상태로는 요청을 보낼 수 없어야 한다.

현재 위치를 사용하는 경우에는 브라우저 위치 권한과 GPS 상태를 확인한다.

위치 오차가 300m보다 크거나 선택 후 2분이 지났다면 다시 선택하도록 안내하는지 확인한다.

### 4.3 운전자가 요청 수락

1. 차량 앱에서 **받은 마중 요청과 픽업 대기 목록** 열기
2. 요청한 탑승자와 장소 확인
3. 요청 수락
4. 탑승자 화면의 **수락됨 · 픽업 대기** 표시 확인

수락은 픽업 시작과 다르다.

이 단계에서 차량 위치가 탑승자에게 공개되지 않아야 한다.

### 4.4 내비게이션 경로 확인 및 픽업 시작

1. 차량 내비게이션에서 최종 목적지 설정
2. 경로 안내 시작
3. 마중 차량 앱에서 내비게이션 경로 확인
4. 요청 장소를 픽업 경유지로 반영
5. SDK 경로 및 장소 일치 여부 확인
6. **이 픽업 시작** 선택
7. 위치 공유 시작 확인

탑승자는 **내 픽업 진행 중**으로 상태가 변경되는지 확인한다.

차량 SDK에서 유효한 위치와 ETA가 전달되면 웹에 해당 정보가 표시되어야 한다.

SDK 정보가 없다면 임의의 도착 시간을 생성하지 않고 정보 대기 상태를 표시한다.

경로 검증이 실패하면 픽업을 강제로 시작하지 않고 실패 이유를 기록한다.

### 4.5 준비 상태 전달

1. 탑승자가 **준비 완료** 선택
2. 웹에 **서버에 저장 · 차량 전달 대기** 표시 확인
3. 차량 앱에서 최신 상태 수신
4. 웹의 **차량 앱에 전달** 표시 확인
5. 차량에서 준비 상태가 반영됐는지 확인

**차량 앱에 전달**은 차량이 상태를 수신했다는 의미다.

운전자가 실제로 화면을 읽었다는 뜻은 아니다.

차량 앱과 공유 서비스를 중단한 상태에서 준비 상태를 변경하는 경우, 이전 상태의 전달 완료 표시가 잘못 유지되지 않는지도 확인한다.

### 4.6 도착 및 탑승 완료

1. 차량이 픽업 장소에 도착한 상황 확인
2. 개발 시험에서는 **도착 알리기 · 공유 유지** 기능으로 도착 상태 확인
3. 운전자가 실제 탑승을 확인
4. **탑승 확인 · 픽업 완료** 선택
5. 탑승자 웹에서 픽업 종료 확인
6. 이전 차량 위치와 ETA가 더 이상 표시되지 않는지 확인

수동 도착 버튼을 이용한 시험은 SDK 자동 도착 이벤트 검증과 구분한다.

다음 픽업을 진행할 때는 **새 픽업 준비**를 통해 다음 요청을 확인한다.

## 5. 연결된 탑승자 직접 초대

이미 연결된 탑승자는 QR코드 없이 차량에서 바로 초대할 수 있다.

### 테스트 순서

1. 운전자와 탑승자가 `/account`에서 로그인
2. 사람 연결 요청 및 수락
3. 운전자가 차량에서 내비게이션 경로와 장소 확인
4. **연결된 탑승자에게 초대 보내기** 선택
5. 초대할 사람 선택
6. 탑승자가 웹의 받은 초대에서 장소 확인
7. 초대 수락
8. 차량에서 대기 상태 확인
9. 해당 픽업 시작 후 위치 공유 확인

수락 전에는 차량 위치가 공개되지 않아야 한다.

다른 픽업이 이미 진행 중이라면 초대받은 탑승자는 대기열에 들어가야 한다.

현재 픽업이 종료된 후 다음 픽업을 진행한다.

### 개발 근거

- [백엔드 PR #18](https://github.com/majung-team/majung-backend/pull/18)
- [웹 PR #17](https://github.com/majung-team/majung-web/pull/17)
- [차량 PR #29](https://github.com/majung-team/majung-vehicle-app/pull/29)

현재 두 계정 간 전체 직접 초대 흐름은 로컬 검증과 실제 휴대전화 검증을 구분해 관리한다.

## 6. 여러 픽업 요청 및 대기열

운전자 1명과 탑승자 2명, 총 3개의 계정으로 확인한다.

### 테스트 순서

1. 첫 번째 탑승자의 픽업 요청
2. 두 번째 탑승자의 픽업 요청
3. 운전자가 두 요청 수락
4. 첫 번째 픽업 시작
5. 두 번째 탑승자의 대기 상태 확인
6. 첫 번째 픽업 완료
7. 다음 장소의 경로 확인
8. 두 번째 픽업 시작

### 예상 결과

- 진행 중인 픽업은 한 건만 유지
- 다른 탑승자의 이름·장소·좌표 비공개
- 대기 중인 요청의 순서 유지
- 앞선 픽업의 ETA를 자신의 도착 예정 시간처럼 표시하지 않음
- 동일 탑승자의 중복 요청 차단
- 첫 번째 픽업 종료 후 다음 요청 진행

대기 중 표시되는 앞선 픽업까지의 남은 시간은 자신의 픽업 장소까지의 ETA와 구분되어야 한다.

### 자동화 테스트

백엔드 저장소에서 다음 명령으로 관련 테스트를 실행할 수 있다.

```sh
./gradlew test --tests '*RideRequestTest'
```

관련 시험 범위:

- 신규 탑승자 여러 명의 요청 및 대기
- 요청 순서 전환
- 동시 수락 처리
- 기존 초대 픽업 중 새 요청
- 중복 요청
- 취소 및 만료
- 타인 접근 차단
- 계정 연결 해제

자동화 테스트의 가상 계정 결과는 실제 휴대전화 다중 요청 검증과 구분한다.

## 7. 장소 변경 제안

픽업 진행 중 탑승자가 새로운 장소를 제안하는 흐름을 확인한다.

### 테스트 순서

1. 탑승자가 **다른 장소 제안하기** 선택
2. 장소명·주소 검색 또는 지도에서 위치 선택
3. 장소 정보와 지도 핀 확인
4. **제안 보내기** 선택
5. 차량에서 제안 카드 확인
6. 정차 상태에서 새 장소의 내비게이션 경로 검증
7. 운전자가 장소 변경 확정
8. 웹에 확정된 장소가 반영되는지 확인

운전자가 확정하기 전에는 기존 픽업 장소를 유지해야 한다.

검색 결과나 지도 핀을 선택한 것만으로 장소 변경이 완료되어서는 안 된다.

[장소 선택 및 준비 상태 관련 검증 기록](readiness-place-2026-10-26.md)

## 8. 연결 중단 및 복구

### 모바일 웹 재접속

1. 픽업 진행 중 웹 상태 확인
2. 브라우저에서 다른 화면으로 이동
3. 다시 마중 화면으로 복귀
4. 서버의 최신 픽업 상태가 반영되는지 확인

### 차량 연결 중단

1. 픽업 진행 중 차량 연결 중단 상황 재현
2. 마지막 위치 및 ETA 표시 확인
3. 정보 유효 시간 만료 시 표시 변화 확인
4. 연결 복구
5. 최신 상태 재조회 및 권한 확인

오래된 위치나 ETA가 계속 현재 정보처럼 표시되어서는 안 된다.

연결 복구 후에도 픽업이 이미 완료됐거나 권한이 철회됐다면 이전 공유가 재개되지 않아야 한다.

## 9. 문제 발생 시 확인

| 증상 | 확인할 내용 |
| --- | --- |
| 사이트가 열리지 않음 | 네트워크 연결, HTTPS 주소, 서버 health |
| 서버는 UP인데 새 버튼이 없음 | 웹 배포 상태, release.json, 새로고침 |
| 웹 요청에서 404 발생 | 서버·웹 버전 및 API 배포 순서 |
| 배포 후 로그인이 풀림 | 재로그인 후 상태 확인. 차량 데이터를 바로 삭제하지 않음 |
| 차량 앱이 서버에 연결되지 않음 | 빌드 API 주소, 차량 인터넷 연결, 등록 상태 |
| 차량 미연결로 요청 불가 | 운전자 계정 연결 및 차량 승인 여부 |
| 같은 닉네임이 여러 개 검색됨 | 마중 ID 확인 |
| 위치 선택 실패 | HTTPS, 브라우저 위치 권한, GPS 정확도 |
| 차량 버튼 조작 불가 | 주행 제한 상태 및 안전한 정차 상태 |
| ETA가 표시되지 않음 | SDK 연결, 경로, 장소 일치 및 정보 유효 시간 |
| 요청 결과가 반영되지 않음 | 서버 상태 재조회. 동일 작업 반복 전 현재 상태 확인 |
| 새 요청이 바로 표시되지 않음 | 차량 앱에서 목록 재확인. 앱 종료 상태의 요청 푸시는 현재 제공하지 않음 |
| APK 설치 실패 | ADB 연결 상태, 파일 경로, 기존 APK 서명 |

서버 장애를 확인할 때는 마중 전용 인프라를 기준으로 점검한다.

다른 서비스의 서버나 설정을 변경하지 않는다.

## 10. 테스트 결과 기록

정상 픽업 흐름을 먼저 확인한 뒤 예외 상황을 시험한다.

문제가 발생했다면 다음 내용을 기록한다.

```text
테스트 날짜:
서버 revision:
웹 revision:
차량 앱 버전 / 커밋:
시험 기기 및 에뮬레이터:
시험한 기능:
발생 단계:
기대한 결과:
실제 결과:
재현 여부:
관련 PR 또는 이슈:
```

공개 이슈와 화면 캡처에는 다음 정보를 포함하지 않는다.

- 초대 링크의 전체 URL 및 비밀 토큰
- 차량 등록 코드와 인증 정보
- 로그인 쿠키 및 세션 정보
- 실제 사용자의 위치 및 개인 주소
- 관리자 키 또는 서버 접근 권한

재현에 필요한 동작 순서와 오류 메시지만 기록한다.
