마중 차량 앱을 켠 운전자는 픽업이 시작되면 곧바로 차량 내비게이션 화면으로 넘어가는 경우가 많다. 만약 운전자가 내비 화면을 보는 동안 마중 앱이 조용히 백그라운드에 머물러만 있다면, 탑승자가 보낸 '지금 내려가요' 메시지나 만날 장소 변경 제안, 대기 중인 새 요청을 놓치게 된다.

반대로 주행 중에 복잡한 버튼과 입력창을 화면에 남겨 두면 차량 UX 제한 정책에 어긋난다. 마중에서는 "내비 화면 위에서 꼭 필요한 변화만 알리고, 앱 화면에서는 주행 제한에 맞춰 읽기 전용으로 접고, 정차 화면의 가독성과 스크롤까지 정리하는" 작업을 순차로 진행했다.

## 내비 화면 위에서도 요청·장소 변경·메시지를 바로 띄우기 (`c0cbcdd`)

처음에는 차량 앱으로 돌아와야만 탑승자 메시지와 요청 상태를 볼 수 있었다. `c0cbcdd`에서는 `VehicleApplication`과 `PickupSharingService`에 고중요도 알림 채널(`pickup-alerts-v2`, `IMPORTANCE_HIGH`, 진동·`VISIBILITY_PUBLIC`·`setBypassDnd(true)`)과 `VIBRATE` 권한을 적용해 내비 위에서도 헤드업 알림이 뜨도록 바꿨다. 이후 주행 중 빠른 메시지 알림의 `확인`을 눌렀을 때 마중 앱으로 화면이 전환되지 않고 내비를 계속 볼 수 있도록 `9983272` · `0.2.34-preview`에서 `USE_FULL_SCREEN_INTENT`와 헤드업 `setFullScreenIntent`·빠른 메시지 `Toast`를 제거하고, 빠른 메시지 `확인`은 알림만 정리하는 `DISMISS_ONLY`(`NotificationDismissReceiver`)로 분리했다.

전달 경로와 음성 발화 기준은 이벤트 성격에 따라 나눴다.

| 이벤트 | 헤드업 알림 · 액션 | Pleos TTS 음성 정책 |
| --- | --- | --- |
| **신규&nbsp;픽업&nbsp;요청**<br>`notifyNewRide` | 헤드업 알림(`요청 확인`)<br>+ 백그라운드 Toast | 발신자 · 요청 장소 라벨<br>짧게 낭독 |
| **빠른&nbsp;메시지**<br>`notifyQuickMessage` | 헤드업 알림(`확인`, 내비 유지)<br>`NotificationDismissReceiver` (`#9983272`) | 발신자 · 메시지 본문 낭독<br>(5초 직렬 대기) |
| **장소&nbsp;제안**<br>`notifyPassengerEvents` | **`수락 및 내비 변경`**<br>원터치 액션 (`#c0cbcdd`) | `"새 장소 제안..."`<br>고정 문구 1회 (이름 비노출) |
| **준비&nbsp;·&nbsp;도착**<br>`PickupVoicePolicy` | 상태 반영 카드<br>요약 화면 전환 | 고정 문구 1회 재생<br>(재개 확인 전 제외) |

- **신규 픽업 요청 (`notifyNewRide`)**: 헤드업 알림(`요청 확인` 액션) + 앱이 백그라운드면 Toast + TTS 안내 (`OPEN_APP_SCREEN`).
- **탑승자 빠른 메시지 (`notifyQuickMessage`)**: 헤드업 알림(`확인` 액션) + TTS 안내 (`DISMISS_ONLY`). 내비게이션을 보던 운전자가 `확인`을 눌러도 마중 앱으로 화면이 넘어가지 않고 `NotificationDismissReceiver`로 알림만 닫히며 내비 화면을 유지한다(`9983272`, `0.2.34-preview`). 웹에서는 `지금 내려가요`, `1번 출구 앞이에요`, `곧 도착해요` 3개 빠른 칩과 최대 50자 직접 입력을 지원한다.
- **장소 변경 제안 (`PickupSharingService.notifyPassengerEvents`)**: 헤드업 알림에 **`수락 및 내비 변경`** 액션을 바로 달았다(`ACTION_ACCEPT_PROPOSAL`). 내비 화면을 보던 운전자가 앱을 다시 열지 않고 알림 액션만 눌러도 `handleAcceptProposal()`이 `autoConfirmProposalId`를 걸어 `changePickupPlace()`로 내비 경유지 반영까지 이어진다.

## Pleos TTS는 무엇을 읽고 무엇을 읽지 않을까?

음성 안내에는 클라우드 인증 키가 필요 없는 Pleos `TextToSpeech 3.3.1`(`Mode.ON_DEVICE`, `Locale.KOREA`)을 `PleosPickupVoiceOutput`으로 감싸 연동했다.

구현하면서 까다로웠던 점 두 가지는 SDK 제약과 오디오 포커스였다.

1. **발화 ID(utteranceId)가 없는 직렬화 처리**: `PleosPickupVoiceOutput` 주석대로 SDK 콜백에 개별 발화 ID가 없어, 재생 도중 다음 메시지가 오면 곧바로 겹쳐 부르지 않고 `pending` 슬롯 1개에 `5초` 유효기간을 걸어 직전 발화가 끝난 뒤 이어서 읽게 했다. 5초가 지나 오래된 안내는 버린다.
2. **오디오 포커스와 비차단 격리**: 내비 안내 음성을 끊지 않도록 `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`(`USAGE_ASSISTANCE_NAVIGATION_GUIDANCE`)을 요청하며 delayed focus는 쓰지 않는다. 초기화(10초)·재생·정지마다 타임아웃을 두어 TTS 엔진이 실패하더라도 위치 공유나 도착 처리를 막지 않는다.

음성 안내 대상은 **상태 변화 안내**와 **실시간 전달 안내**를 나눴다.

- `PickupVoicePolicy`가 감시하는 픽업 상태 전이(`READY`, `PROPOSED`, `ARRIVED`)는 개인정보 노출을 막기 위해 탑승자 이름, 마중 ID, 장소 이름을 읽지 않고 고정 문구(`"탑승자가 준비를 마쳤어요."` 등)만 1회 재생한다. 앱 재실행 후 복구 과정에서 들어온 과거 상태나 공유 재개 확인 전 상태는 재발화하지 않는다.
- 반면 운전자가 방금 도착한 요청이나 메시지를 화면을 못 보고 파악할 수 있어야 하는 `notifyQuickMessage()` / `notifyNewRide()` 경로는 `voice.speak(...)`로 발신자와 내용·장소 라벨을 짧게 읽어 준다. (설정에서 음성 안내를 끄면 이후 안내와 재생 중인 음성도 즉시 멈춘다.)

## 주행 중 조작 제한(`CarUxRestrictions`)은 어떻게 맞췄을까?

마중은 차량 속도나 기어 값을 직접 해석해 주행 여부를 추측하지 않는다. `DrivingRestrictionMonitor`가 AAOS `CarUxRestrictionsManager`의 `isRequiresDistractionOptimization` 및 활성 제한 플래그(`UX_RESTRICTIONS_LIMIT_STRING_LENGTH`, `UX_RESTRICTIONS_LIMIT_CONTENT`)와 변경 콜백을 그대로 따른다.

- 주행 제한이 켜지면 `MainActivity`는 정차 화면(`parked_controls`)과 기존 확인창(`views.trackDialog`로 추적된 `AlertDialog`)을 전부 닫고 읽기 전용 요약(`driving_summary`)만 표시한다. `stringLimit`과 `itemLimit`도 시스템 제한 값에 맞춰 카드 문자열 길이와 표시 개수를 줄인다.
- `DrivingPickupSummary`는 이름·좌표·대기열 ETA를 빼고 진행 단계(`phase`), 준비 상태 또는 최근 메시지 한 줄(`readiness` / `메시지: “...”`), 남은 시간(`eta`) 3요소만 남기며 클릭·스크롤 가능한 요소를 두지 않는다.
- 도착 판정(`PickupArrivalEvidence`) 역시 ETA가 0초라는 이유만으로 자동 확정하지 않고, 경로 목표 일치 + 반경 `100m` 이내 + 잔여 시간 `30초` 이하(도착 콜백 동반 시 `60초`) 조건을 만족할 때 도착으로 넘기되, 실제 **탑승 완료** 처리는 정차해 주행 제한이 풀린 뒤 운전자가 직접 누르도록 분리했다.

## 가독성·기본 스크롤 개선과 에뮬레이터 테스트 실패 기록 (`#115`, `#117`)

정차 화면 사용성도 한 번 크게 다듬어야 했다. 초기 화면에서는 탑승자 이름과 메시지가 붙어 잘리거나 버튼 위계가 평평했고, 설정/목록 스크롤에서 휠 입력마다 고정 픽셀을 계산해 움직임이 부자연스러웠다.

11월 5일 PR [#115](https://github.com/majung-team/majung-vehicle-app/commit/fcd03dc22658b52cd06bcbebfed0a74201ca9878)에서는 다음을 바꿨다.

- `PickupStatusSection`에서 탑승자 이름(`passenger`)과 메시지 카드(`passengerMessage`)를 분리하고 메시지가 여러 줄로 자연스럽게 줄바꿈되도록 배치했다.
- 시작/초대 같은 주 행동 버튼을 강조하고 새로고침·연결 관리·취소는 보조 버튼으로 낮췄다.
- 고정 거리 휠 스크롤 계산을 제거하고 Android 기본 `ScrollView`(`createSmoothScrollView()`)를 따르게 했다.

> [!WARNING]
> **에뮬레이터 계측 시험 실패 기록 (`#116`, PR `#117`)**: `VehicleReadabilityTest`를 공식 Pleos 에뮬레이터에서 실행했을 때 화면 캡처(`settings.png`, `search.png`, `completed.png`)까지는 정상 생성됐지만, 종료 단계에서 `ActivityScenario.close()`가 `DESTROYED`를 기다리는 동안 액티비티가 `PAUSED` 상태에 남아 전체 계측 시험은 실패했다([`docs/usability-2026-11-05.md`](https://github.com/majung-team/majung-vehicle-app/blob/main/docs/usability-2026-11-05.md)). 단위 시험·Lint·빌드 통과와 별도로 **"기기 자동 계측 미통과"**로 구분해 유지한다.
