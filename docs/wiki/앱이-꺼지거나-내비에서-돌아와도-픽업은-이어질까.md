차량용 앱은 일반 스마트폰 앱보다 화면 전환과 백그라운드 이동이 잦다. 픽업 초대를 만든 뒤 내비게이션 화면으로 넘어가기도 하고, 앱이 메모리에서 정리되거나 사용자가 강제 종료한 뒤 다시 열릴 수도 있다.

문제는 **단순히 로컬에 마지막 픽업 상태를 저장해 두고 앱이 켜질 때마다 바로 위치 공유를 재개하면 위험하다**는 점이었다. 이미 끝난 픽업에 과거 위치나 ETA를 다시 보낼 수도 있고, 운전자가 의도하지 않은 시점에 위치가 다시 전송될 수도 있기 때문이다.

## 화면 이탈과 프로세스 종료는 다르게 다뤄야 했다

마중 차량 앱은 화면에서 내려간 경우와 프로세스가 죽은 경우를 아예 다른 계층으로 나눴다.

| 상황 | 동작 계층 | 보호 · 복구 규칙 |
| --- | --- | --- |
| **공유&nbsp;중&nbsp;이동**<br>`onStop()` | `PickupSharingService`<br>(`LOCATION`) | Foreground 1초 동기화 유지<br>`START_NOT_STICKY` |
| **확인&nbsp;중&nbsp;이동**<br>경유지·장소 | `MainActivity` +<br>`DestinationReader` | `#132` 50초 유예<br>내비 복귀 시 경로 자동 검증 |
| **강제&nbsp;종료**<br>재실행 | `EncryptedPickup`<br>`SessionStore` | 자동 공유 금지 · 서버 조회<br>운전자 재개 확인 시 복구 |

- **내비 등 다른 화면으로 이동 (`MainActivity.onStop`)**: 이미 시작된 `PickupSharingService`가 Foreground Service(`FOREGROUND_SERVICE_TYPE_LOCATION`)로 남아 SDK 연결과 1초 주기 상태 동기화를 계속 유지한다. 단, `onStartCommand`는 `START_NOT_STICKY`로 둬서 프로세스 강제 종료 후 시스템이 멋대로 재시작해 오래된 상태로 공유를 이어가지 않게 했다.
- **아직 공유가 시작되기 전, 내비 화면으로 넘어갔을 때 (`#132`, `6d599f1`)**: 이전에는 `onStop`이 호출될 때 `!app.sharingRunning`이면 `app.destination.disconnect()`를 바로 호출해, 경유지 추가나 장소 변경 확인 도중 Pleos가 내비를 전면으로 띄우면 진행 중인 SDK 요청이 끊겼다. `#132`에서는 `addingWaypoint`, `checkingPlaceProposal`, `RequestPickupFlow.Stage.PREPARING` 중일 때 즉시 끊지 않고 `50초`(`disconnectIdleNavigation`) 유예를 두었고, `onResume`으로 돌아오면 `autoConfirmProposalId`가 걸린 제안의 경로 검증(`reviewProposedPlace`)을 자동 이어가도록 맞췄다.
- **OS 프로세스 종료 또는 강제 중지 후 재실행**: 자동 재실행하지 않는다. 운전자가 앱을 다시 열었을 때 암호화 저장소를 읽어 서버 상태를 먼저 검증하고, 명시적인 재개 확인을 거친 뒤에만 공유를 다시 시작한다.

## 왜 `EncryptedSharedPreferences`를 쓰지 않았을까?

안드로이드에서 작은 인증 정보를 암호화해 저장할 때 흔히 떠올리는 `androidx.security.crypto.EncryptedSharedPreferences`는 Android 공식 API 문서에서 **deprecated**로 표시돼 있다. 작은 픽업 세션 하나 때문에 deprecated 라이브러리와 SharedPreferences XML 캐시에 의존할 이유가 없었다.

대신 `EncryptedPickupSessionStore`를 직접 작성했다. 구조는 단순하다.

```text
Android Keystore (AES-256-GCM, alias = "majung.pickup-session.v1")
  ├─ AAD: "majung-session-v1:" + BuildConfig.PICKUP_API
  ├─ Payload: version(1), pickupId, driverToken, inviteToken,
  │           vehicleSequence, navigationReference
  └─ 저장 위치: noBackupFilesDir/pickup-session.bin (AtomicFile)
```

구체적으로 네 가지 안전장치를 넣었다.

1. **API origin 바인딩 (AAD)**: 암호화와 복호화 모두 `BuildConfig.PICKUP_API`와 버전 문자열을 GCM Associated Data(`updateAAD`)로 넣는다. 개발/로컬 시험 빌드와 운영(`majung.cloud`) 빌드의 세션 파일이 섞여 복호화되는 일을 원천적으로 막는다.
2. **백업 제외·원자적 쓰기·평문 폴백 금지**: 클라우드 백업 대상이 되지 않도록 `noBackupFilesDir`를 사용하고, 쓰기 도중 강제 종료돼도 파일이 깨지지 않게 `AtomicFile`을 사용한다. Keystore 키가 없거나 암호문이 변조되면 복호화 실패를 내고 파일을 삭제할 뿐, 평문으로 내려서 저장하지 않는다.
3. **최소 필드만 저장 (`SavedPickupSession`)**: 주석(`Location and passenger names are deliberately not part of the saved session`)대로 위도·경도, ETA, 탑승자 이름, 장소 라벨은 로컬 파일에 저장하지 않는다. 복구에 꼭 필요한 `pickupId`, 43자 토큰(`driverToken`, `inviteToken`), 마지막 전송 순번(`vehicleSequence`), 그리고 ID 없는 경유지 재대조용 `navigationReference`만 남긴다.
4. **삭제 확인 후 새 픽업 허용**: 완료·취소·만료·4xx 오류(`401`, `403`, `404`, `410`) 시 `clear()`로 기본 파일과 `.bak` 파일이 모두 지워졌는지 검사한다. 삭제에 실패하면 새 픽업 생성 자체를 막아 이전 세션이 되살아나지 않게 한다.

## 강제 종료 뒤에도 자동 공유 대신 '운전자 확인'을 둔 이유

`VehicleApplication`이 생성 직후 `restoreSession()`을 호출해 저장 파일이 발견되면 상태가 `RESTORING`으로 들어가고, 새 픽업 생성은 잠시 막힌다. 그다음 흐름은 다음과 같다.

```text
저장 파일 로드 -> 서버 조회 (/api/v1/pickups/{id})
  ├─ COMPLETED / CANCELLED / EXPIRED 또는 401/403/404/410
  │    └─ 로컬 세션 즉시 삭제
  ├─ 네트워크 끊김 / 5xx
  │    └─ 세션 유지 · 과거 위치 전송 없이 재확인 대기
  └─ ACTIVE / ARRIVED 확인
       └─ needsSharingConfirmation = true ("이전 픽업 계속하기")
            └─ 운전자 확인 -> 새 SDK 수신 -> sequence + 1로 재개
```

> [!IMPORTANT]
> 서버에서 `ACTIVE`로 확인됐더라도 **운전자가 `이전 픽업 계속하기`를 누르기 전에는 `PickupSharingService`를 띄우지 않고 `syncVehicle()`에서 위치·ETA 전송을 막는다.** 앱이 꺼진 사이에 운전자가 이미 탑승자를 다른 방법으로 만났거나 경로를 바꿨을 수 있고, 재실행 직후 SDK에서 아직 새 좌표가 오기 전에 옛날 값을 올리면 탑승자 화면이 엉뚱한 시간을 보여줄 수 있기 때문이다.

또한 경유지로 생성된 픽업이었다면 저장해 둔 `navigationReference`(`majung:...` 등)와 서버가 돌려준 확정 장소 좌표를 다시 `DestinationReader.restorePickupReference()`에 넣고, 새 SDK 경로 응답과 대조가 끝나야 경유지 ETA를 다시 보내도록 묶었다.

- 실제 차량 시동 OFF/ON(AAOS 전원 차단 및 복귀), 기기 재부팅 직후 복구, 실제 하드웨어 Keystore 백업 동작은 실차에서 시험하지 못했다.
- 사용자가 앱을 강제 종료한 뒤 다시 실행하지 않은 상태에서 백그라운드로 되살아나는 동작은 의도적으로 지원하지 않는다.
