픽업 서비스에서 위치를 공유할 때보다 더 까다로운 지점은 **언제 정확히 멈추는가**다. 약속이 끝났거나, 사용자가 카카오 연결·차량 연결을 끊었거나, 초대가 만료됐는데도 백엔드 푸시 구독이나 웹 카운트다운, 미확정 장소 제안이 남아 있으면 불필요한 추적이나 오인 안내로 이어진다.

---

## 도착·연결 해제 시 남은 제안과 푸시 차단 (`#64`, `ea55d33`)

초기 구현에서는 픽업 상태가 종료되거나 계정 연결이 끊길 때 주변 정리가 일부 빠져 있었다.

1. 픽업이 도착(`ARRIVED`) 또는 종료 상태로 넘어갈 때, 아직 확정되지 않은 `PlaceProposal`이 남아 있을 여지가 있었다.
2. 사용자가 카카오 계정 연동을 해제(`KakaoUnlinkService`)하거나 차량 등록·운전자 계정 연결을 끊더라도, 진행 중이던 픽업의 미확정 제안과 웹 푸시 도착 알림 구독(`ArrivalPushService`) 정리가 함께 묶여 있지 않았다.

PR [#64](https://github.com/majung-team/majung-backend/commit/ea55d33cd3f554ebb04b988cd2683c3d3fd25bbd)(이슈 [#63](https://github.com/majung-team/majung-backend/issues/63))에서 이 경계를 한 트랜잭션 안으로 모았다.

| 트리거 | 서버 트랜잭션 정리 | 차단 결과 |
| --- | --- | --- |
| **도착·종료**<br>`ARRIVED` | `Pickup.clearProposal()` 호출 | 미확정 장소 제안 잔존 차단 |
| **계정&nbsp;해제**<br>카카오·차량 | 진행 중 픽업 `CANCELLED` 전환<br>`inviteHash`·`clearProposal()`<br>`clearVehicle()` | 조회 · 추적 · 웹 푸시<br>(`arrivalPush.remove`) 중단 |
| **초대·요청**<br>만료·재시도 | `invitation-preview` 비소비 조회<br>종결 요청 `submit(oldInput)` 409 | 만료 링크 `410` 차단<br>과거 요청 부활 차단 |

- `Pickup.clearProposal()`을 두고 도착·종료 전이에서 미확정 장소를 바로 비운다.
- `KakaoUnlinkService`, `VehicleAccountService`, `VehicleRegistrationService`가 연결 해제/철회를 처리할 때 진행 중 픽업을 즉시 `CANCELLED`로 바꾸고, `inviteHash`·`clearProposal()`·`clearVehicle()`과 `arrivalPush.remove(pickup.id)`를 함께 호출해 조회·추적·푸시 발송이 바로 멈추도록 했다(`PlaceProposalTest`, `RideRequestTest`).

## 만료·취소된 초대와 요청이 뒤늦게 살아나지 않게 막기 (`10ee898`, `fbd5d09`, `#71`)

종료된 뒤의 차단만큼, 시작 전후의 상태 경계도 문제였다.

- **참여 전 초대 사전 확인 (`10ee898`)**: 탑승자가 초대 링크를 열었을 때 이미 사용되었거나 재발급(rotate)되거나 30분이 지나 만료된 토큰이면 참여 시도 전에 명확히 걸러내야 했다. `POST /api/v1/pickups/{id}/invitation-preview`를 추가해 토큰을 소비하지 않으면서 `placeLabel` 하나만 돌려주고, 유효하지 않으면 `410 INVITE_UNAVAILABLE`을 반환하도록 검증했다(`PickupApiTest`).
- **만료된 초대 QR 차량 내 재발급 (`fbd5d09`)**: 초대가 만료(`INVITE_EXPIRED` 또는 `needsNewInvitation`)됐을 때 운전자가 픽업을 처음부터 다시 만들지 않도록 `PickupController.renewInvitation()`과 `PickupParticipantSection`의 `[새 초대 QR 만들기]` 버튼을 붙여 같은 장소 기준으로 새 초대 토큰을 발급하게 했다.
- **취소·만료 요청의 재요청 회귀 방어 (PR [#71](https://github.com/majung-team/majung-backend/commit/f92e08470846103a136de178567a95760b26ba88), 이슈 [#70](https://github.com/majung-team/majung-backend/issues/70))**: 네트워크 지연으로 취소·만료된 요청 페이로드가 뒤늦게 다시 들어와도(`submit(oldInput)`), 과거 요청(`CANCELLED`/`EXPIRED`)은 종결 상태 그대로 돌려보내고 `409`로 수락을 막으며, 새 `requestId`로 보낸 대체 요청만 `PENDING` 대기열에 남는지 `RideRequestTest`에 회귀 시험을 추가했다.

## 서버 `ageMillis`와 웹 `model.js` ETA 이중 차감 막기 (`e628eea`)

탑승자 모바일 웹에서 남은 도착 시간(ETA)을 계산할 때는 **서버와 클라이언트가 경과 시간을 두 번 빼는 실수(이중 차감)**가 나기 쉽다. 만약 서버가 `durationSeconds`에서 이미 흐른 시간을 깎아서 내려주고, 웹이 다시 `ageMillis`를 빼면 남은 시간이 실제보다 두 배 빨리 줄어들게 된다.

이를 막기 위해 백엔드와 웹이 같은 계약을 나누어 맡도록 정했다.

- **서버**: 차량 앱이 마지막으로 올린 원본 `durationSeconds`를 깎지 않고 그대로 내려주고, 현재 서버 시각 기준으로 얼마나 지난 정보인지 `ageMillis`와 남은 신선 유효 시간 `validForMillis`, 그리고 `freshness`(`FRESH` / `STALE`)를 함께 응답한다.
- **웹 (`majung-web/model.js`)**: 탑승자 휴대폰의 시계(`Date.now()` 벽시계 오차)를 믿지 않고, HTTP 요청 왕복 시간(`responseReceived - requestStarted`)과 응답 수신 이후 흐른 시간(`now - timing.at`)만을 이용해 `vehicleTiming`, `vehicleDeadline`, `vehicleView`를 계산한다.
  - `ageMillis >= 30초` 부근에서 `STALE` 표시(만료 직전 마지막 예상 유지)
  - `ageMillis >= 120_000ms` (`COUNTDOWN_STOP_MILLIS`)에 달하면 `lost` 처리해 카운트다운을 중단하고 위치/ETA를 숨김

> [!NOTE]
> `PickupApiTest.exportsRawEtaAndFreshnessResponsesForDeployedWebCompatibility`가 실제 HTTP 응답 JSON(`build/contracts/eta-api-responses.json`) 5가지 시나리오를 생성하고, Node 계약 스크립트(`deploy/test_eta_contract.mjs`)가 이를 실제 `../majung-web/model.js`에 넣어 검증한다.

| 시나리오 | 서버 응답 (`durationSeconds`, `ageMillis`) | 웹 `model.js` 결과 |
| --- | --- | --- |
| **정상&nbsp;20초** | 원본 `180초`, `ageMillis = 20000` (미차감) | `fresh` · `159초`<br>(이중 차감 없음) |
| **30초&nbsp;지연** | `ageMillis >= 30000` | `stale` · `149초`<br>(마지막 예상 유지) |
| **2분&nbsp;단절** | `ageMillis >= 120000`<br>(`COUNTDOWN_STOP_MILLIS`) | `lost` · 카운트다운 중단<br>위치·ETA 숨김 |
| **정체·단축** | 새 ETA `600초` / `120초` | 이전 값 폐기 →<br>`599초` / `119초` |
| **오프라인·종료** | `online = false` 또는 `COMPLETED`·`CANCELLED` | `null` 반환<br>(남은 시간 즉시 숨김) |

## 지도 연결이 실패했을 때 빈 카드 남기지 않기 (`#110`, `30e28d2`)

탑승자 웹에서 카카오 지도 SDK 로딩이 실패하거나 `place` 정보가 아직 없을 때도 기존에는 `.map-wrapper.no-map` 빈 회색 박스가 화면 한가운데 남았다. 게다가 지도 오류가 났을 때 도착 시간까지 지도 영역 안에 들어 있으면 안 됐다.

웹 PR [#110](https://github.com/majung-team/majung-web/commit/30e28d25fea3448d5cd1a85f13cb4c3820854716)에서는 `.map-wrapper.no-map` 스타일과 빈 컨테이너를 제거해 `pickupMap && snapshot.place`가 모두 유효할 때만 `.map-wrapper`와 `차량·만날 장소 다시 보기` 버튼을 렌더링하도록 정리했다. 도착 시간 요약(`.pickup-eta-summary`)과 `[지도 다시 불러오기]` 복구는 지도 카드 밖에 두어, 지도가 실패해도 ETA와 약속 장소 확인이 가리지 않게 했다(`test/app-reentry.test.js`).

## 확인한 것과 확인하지 못한 것

**확인한 내용**

- `PickupApiTest`, `PlaceProposalTest`, `RideRequestTest` (로컬 HTTP + DB 통합 시험): 도착 시 미확정 제안 정리, 카카오/차량 해제 시 취소 및 푸시 구독 제거, 참여 전 초대 확인 `410`, 취소/만료 요청 부활 차단 확인.
- `PickupApiTest` → `node deploy/test_eta_contract.mjs ../majung-web/model.js`: HTTP 응답 5개 시나리오와 오프라인/종료 상태 숨김 계약 확인.
- `majung-web/test/app-reentry.test.js`: 지도 실패 시 빈 `.map-wrapper` 미렌더링 및 ETA 요약 유지 확인.

**확인하지 못한 점**

- 실제 모바일 브라우저 백그라운드 슬립이나 iPhone OS 저전력 모드에서의 실제 Web Push / APNs 배너 도달 지연 시간.
